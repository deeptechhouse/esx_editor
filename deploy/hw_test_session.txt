## On the machine, in this order. STOP at the first one that misbehaves.
#   t0_identical  byte-identical      -> proves the card/transfer path only
#   t1_tempo      2-byte field        -> confirms the 1/128 BPM scale
#   t2_step       1 bit               -> confirms step bit order and origin
#   t3_sample     1 field             -> confirms the sample-number field
#   t5_motion     one motion slot     -> confirms motion writes
#   t4_commit     a whole new sample  -> confirms the entire commit path
#   t6_song       a 4-position song   -> confirms the song chain WRITES correctly
#   t7_ccprobe    CC 95..127 in rows  -> names the CC-assign rows (see below)
#
# The generator prints exactly what to look at for each. Write down what you
# actually see, especially for anything that differs.

## The CC assign table is NAMED as of 2026-08-26 - nothing to collect.

#
# t7_ccprobe remains worth loading, for a different reason: it checks that this
# editor WRITES the table where the machine reads it. Spot-check the four knobs
# the generator names. Reading a format right does not prove writing it right.

## SAVE EACH t-BANK BACK — the half the eyeball test cannot reach
#
# After you have loaded a t-bank and looked at it, Save All back to the card
# before moving to the next one. Any filename: routing is by the tN token, so
# the machine's own T3.ESX is fine.
#
# This answers a different question from the display. The display says whether
# the machine UNDERSTOOD what we wrote; the return trip says whether it
# PRESERVED it. A machine that silently normalises or repairs a field looks
# perfect on screen and only gives itself away in the bytes coming back.
#
# Copy the returned files into hw_test/readback/ and:
python3 deploy/hw_readback.py
#
# It reports, per test, whether each written value survived - and lists any
# file it could not route rather than ignoring it.
