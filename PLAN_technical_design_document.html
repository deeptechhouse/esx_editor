01Goal

Produce a Technical Design Document complete enough that implementation can begin without further architectural research. The TDD must specify, to byte-level precision where relevant:

  • A read/write codec for the .esx bank format that round-trips byte-identically.
  • A staging-bank workflow: add sample → auto-convert to machine format → analyse key → display → commit to a slot.
  • A drawable, previewable motion-sequence editor — the highest-risk and highest-value feature.
  • A wizard that walks a first-time user through every setting.
  • Deterministic temp-file lifecycle (auto-clear on close, manual "Clear" button, crash-safe).

Headline finding

Every hard question is now answered from primary sources. The .esx format is fully mapped, and drawing motion sequences offline is confirmed feasible — a motion sequence is literally a 128-point, 8-bit envelope. No reverse-engineering remains on the critical path. The two features you care most about are precisely the two the reference project lacks.

Design consequence — "New bank" must start from a template, not from zeros

Four regions are marked unknown and were never decoded. A writer that zero-fills them risks producing a bank the hardware rejects or silently mis-loads. The reference project sidesteps this by shipping defaults/default.esx and treating "new" as "load the blank template, then edit". The TDD must adopt the same rule and the codec must copy unknown regions through byte-for-byte on every write.

03The motion-sequence question, answered

You flagged this as highest priority. Here is the definitive answer, decoded from ParametersMotionImpl.java.

Binary structure

Pattern chunk offset 1160 → 24 motion slots, 130 bytes each:

  struct MotionSlot {          // 130 bytes
      uint16  operationNumber; // WHICH parameter is automated (0–501, see table)
      uint8   value[128];      // ONE VALUE PER STEP
  }

Why 128 values is exactly right

LastStep is an enum of 1–16 and PatternLength is 1–8 bars. Maximum steps = 16 × 8 = 128. Note-gate and note-data arrays are also 128. So the array is one motion value per sequencer step — not an oversampled or time-based curve.

ANSWEREDCan motion sequences be drawn in advance? Yes — unambiguously.

A motion sequence is a 128-point, 8-bit envelope bound to a named target parameter. That is exactly a drawable curve. There is no timing model, no interpolation metadata, no variable-rate encoding, and no hidden state to reconstruct. Drawing one is a solved UI problem: an array editor over a fixed grid. This is the single most encouraging finding of the research.

What can be automated — 313 decoded targets

The reference project's enum looks undecoded (literals are hex placeholders like OP_1E5) but the human-readable name is carried in each literal's third argument. The full table is extracted to research/motion_operation_table_313.tsv.

Effects (op 484–501)484 FX1 Type · 485 FX1 Edit1 · 486 FX1 Edit2 · 487 FX1 Motion Seq SW · 488–491 FX2 · 492–495 FX3 · 501 FX Chain

The 16 effect types

Each FX unit has exactly two continuous controls (Edit1, Edit2) plus a type selector — so previewing "the effect moving" means animating two knobs per unit across three units.

Reverb · BPM Sync Delay · Short Delay · Mod Delay · Grain Shifter · Cho/Flg · Phaser · Ring Mod · Talking Mod · Pitch Shifter · Compressor · Distortion · Decimator · EQ · LPF · HPF

Playback semantics (from the manual)

  • SMOOTH — values interpolate continuously between steps.
  • TRIG HOLD — the value is latched at note-on and held until the next trigger.

The editor must render both modes differently (a smooth polyline vs. a stepped staircase), because the same 128 bytes sound completely different under each.

The one real gap: value domains

The table gives each target's name but not its range. Not every parameter is 0–127 — Reverse is boolean, Filter Type and FX Type are small enums, Pan is bipolar, Level is 0–127. A drawing tool that lets you scribble 0–127 into a boolean field will write banks that behave bizarrely on the hardware.

Therefore: the TDD needs a target-descriptor table mapping each operation number → {kind: continuous | enum | boolean, min, max, labels, display} so the canvas snaps and quantises correctly per target. Deriving it is Spike B below; it is the only genuine unknown left, and it is bounded work — the ranges are readable off the part-parameter definitions in the same model plus the manual's parameter list.

03bManual findings (Rev 2) — two spikes closed

The official Owner's Manual resolved both blocking spikes and surfaced four design rules that were not visible from the reference source code alone.

Spike B is now largely closed — the value-domain table exists in the manual

Manual p.71 prints the complete MOTION DEST → MOTION VALUE table. Extracted, corrected, and checked into research/motion_target_domains.tsv. Spike B shrinks from "derive 313 domains from scratch" to "confirm a 26-row table byte-level against a real bank."

The per-step Disabl sentinel — a third state the canvas must model

Every motion target accepts Disabl at any individual step, meaning do not update the parameter at this step. This is not a value — it is the absence of one.

Design consequence

A motion sequence is not a plain 128-byte envelope, as Rev 1 assumed. It is 128 slots each holding either a value or "no change". The canvas therefore needs an explicit disabled state per step (rendered as a gap, not as zero — drawing zero is musically the opposite of leaving the parameter alone), an eraser tool distinct from the pencil, and a byte-level encoding for the sentinel that Spike B must identify.

Nine targets ignore SMOOTH entirely

Manual p.69: AMP EG, ROLL, REVERSE, FX SELECT, FX SEND, MOD TYPE, MOD DEST, BPM SYNC and FILTER TYPE always play back as TRIG HOLD even when SMOOTH is selected. These are exactly the discrete targets. The editor must render them as latched staircases regardless of the part setting, or it will show curves the hardware will never produce.

Correction to Rev 1 — the sample-rate rationale was wrong, the requirement was right

Rev 1 stated the ESX-1 requires 16-bit/44.1 kHz. It does not. Manual p.88: the machine accepts 8 or 16-bit at 11 025–96 000 Hz, in WAV or AIFF. For any rate other than 44 100 it compensates by adjusting the sample's Tune parameter so playback pitch is correct.

That compensation is real and sufficient. The reference implementation's formula is SampleTune = 12 × log₂(rate / 44100) — semitones, not cents (22 050 Hz maps to exactly −12.00, one octave). Against the ±64.00 field range, every supported rate fits with room to spare.

Your requirement to pre-convert is still correct — but for these reasons instead:

RateTune neededMemory vs 44.1k
22 050 Hz−12.000.50×
44 100 Hz+0.001.00×
48 000 Hz+1.471.09×
96 000 Hz+13.472.18×
  • Memory. Total sample RAM is ~25 MB / 285 s. A 48 kHz sample costs 9% more for identical audio; 96 kHz costs 118% more. Converting is a direct, permanent capacity win on a very tight budget.
  • The Tune field stays at 0.00. Otherwise every off-rate sample lands pre-detuned by an odd offset, and musical retuning becomes arithmetic against a non-zero base.
  • Conversion quality. Offline resampling (ffmpeg/soxr) is far better than the machine's real-time playback-rate interpolation.
  • 8-bit is zero-padded into 16-bit (low byte zeroed), so importing 8-bit wastes half the resolution of the memory it occupies.

Net effect on the design: nothing changes — the converter still normalises everything to 16-bit/44.1 kHz. But the wizard should explain it as an optimisation, not as a hardware requirement, and an "import at native rate" escape hatch is legitimate to offer.

Loop points: the smpl chunk overwrites End on import

Manual p.88: the ESX-1 reads the WAV smpl chunk, imports the first loop only, and overwrites its End parameter with the chunk's Loop End. So a stray smpl chunk in a source file will silently redefine where the sample ends on the machine.

The converter must therefore treat smpl as authoritative output, not incidental metadata: strip inherited chunks by default, and write loop points deliberately from the staging UI. Export writes Manufacturer 0x42, Product 0x71, MIDI Unity Note 0x3C, one loop. Also note AIFF is import-only — export is WAV exclusively.

04A requirements conflict you need to resolve

Key suffixes do not fit in the machine's 8-character sample name

You asked that the detected key be appended to the filename in both classic and Camelot notation. The ESX-1 slot name field holds 8 characters. A name like kick_Am_8A is 10 characters and would be truncated to kick_Am_ — losing the Camelot code and leaving a trailing underscore on the hardware display.

Resolution — two separate namespaces:

  • Staging filesystem name (your library on disk, no length limit): the complete kickdrum_Am_8A.wav — both notations in full, which is where they are actually useful for browsing and reuse.
  • ESX slot name (the fixed 8 bytes at offset 0 of the sample header): the packed convention specified below.

Slot-name convention (specified by Andy, 2026-08-09)

  [a|b]  [NN]   [classical]   [tail of name, uppercased]
    │      │          │              │
    │      │          │              └─ as many chars as still fit, taken from the
    │      │          │                 END of the basename (before .wav/.aiff/.mp3)
    │      │          └─ classical key notation
    │      └─ Camelot number, zero-padded to 2 (sorts correctly; 10–12 need 2 anyway)
    └─ Camelot letter FIRST (a = minor, b = major)

  total = 8 bytes, hard limit

Taking the name from the tail is a deliberate and good choice: trailing characters are what distinguish numbered variants (kick01 / kick02), so the tail carries more information than the head.

Budget analysis — the classical field is what squeezes the name

Recommendation: short-form classical. It preserves both notations as specified while leaving 2–4 characters of name. Long form leaves at most one character and nothing at all for any sharp or flat key — which is 10 of the 24 Camelot positions. The style is a user setting either way, with a live 8-character preview before commit.

Two details to settle

  • Camelot ↔ classical must stay consistent. They are a bijection: 8A is always A minor, 8B always C major. The worked example a08Cmaj pairs 8A with C major; the generator derives the classical form from the Camelot value so the two can never disagree.
  • Character set is unverified. The manual never lists which characters the LCD can render, and the field is raw bytes with no documented encoding. Whether # and lowercase are displayable is unknown — derive the set empirically by collecting distinct name bytes across factory banks (Spike A), with s/b substitutions as fallback.

Reference implementation of the rule: research/naming.py.

CONFIRMED IN REV 2 — the Owner's Manual (p.34) states you "can assign a name of up to eight characters to the sample", and the LCD shows only six of them at a time. The limit is real and official; the two-namespace resolution above stands.

Hardware access changes the verification strategy

With a real ESX-1 and card on hand, every open question resolves by the same method: set one thing on the machine, save to card, diff the bytes against the previous save. That is far stronger than inferring from factory banks.

UnknownIsolating experiment
Disabl sentinel encodingRecord a motion sequence, set one step to Disabl, save. Diff against the same bank with that step set to a value. The single changed byte is the sentinel.

Bipolar encoding (Pitch, Pan, EG Int)Set Pan hard left, centre, hard right on three steps; save; compare. Distinguishes offset-64 from sign-magnitude.

Full-scope editing raises the stakes on the round-trip gate

Because v1 writes every region rather than only the sample area, a defect anywhere in the codec can corrupt patterns, songs, or global settings — not just samples. Two consequences for the TDD:

  • The round-trip corpus must exercise every region, and the gate is byte-identity across all of them, not just the parts v1 happens to edit.
  • Write-side safety is non-negotiable: never write in place, always verify by re-reading and comparing the parsed model against what was intended, and keep the previous bank recoverable.

Temp-file lifecycle must survive a crash

"Delete on close" is not sufficient — it does nothing if the process is killed. The TDD will specify a session directory named with a PID + timestamp and guarded by a lockfile, plus an orphan sweep at startup that removes session dirs whose owning PID is gone. This is the difference between a tidy tool and one that silently fills a disk with converted WAVs.

05bPer-sample quality budget NEW FEATURE

Proposed 2026-08-09: let the user spend the bank's fixed memory deliberately — full fidelity on what matters (a vocal, a kick), reduced fidelity on what doesn't — with CD quality as the default. The research says this is not only feasible but is exactly what Korg themselves did: the factory bank spans eight rates from 22 050 to 48 000 Hz.

One correction: bit depth buys you nothing

Only sample rate reduction saves memory. Bit depth does not, for two independent reasons:

  • The .esx stores PCM at 16-bit always — MAX_SAMPLE_BYTES = frames × 2, and every factory sample's byte length divides by 2 into a musically plausible duration.
  • The manual (p.88) states 8-bit input is expanded into 16-bit by zero-filling the low byte on import. An 8-bit source therefore occupies exactly the same space as a 16-bit one, while sounding worse.

So the quality axis is rate only. Bit-depth reduction remains available as a purely aesthetic effect (bitcrush baked into the audio), but it must never be presented as a way to fit more in the bank.

What rate reduction actually buys

Memory is linear in rate, so the arithmetic is clean. Total capacity is 25 165 824 bytes:

TierRateBytes/secSeconds in a full bankGainTune cost
CD — default44 10088 200285.31.00×0.00 st
Broadcast32 00064 000393.21.38×−5.55 st
Radio22 05044 100570.72.00×−12.00 st

Telephone11 02522 0501141.34.00×−24.00 st

Halving the rate doubles the bank. That is a big lever on a machine with only 285 seconds.

The strategy insight: target long, not merely unimportant

Savings scale with duration × rate reduction, so where the bytes are is not always where the musical unimportance is:

  8 s vocal loop   44.1k -> 22.05k   saves 352 800 B
  0.4 s hi-hat     44.1k -> 11.025k  saves  26 460 B   (13x less, at 4x the quality cost)

Downgrading every hi-hat in a kit is mostly wasted effort. One long loop dropped a tier frees more than a dozen one-shots crushed to telephone quality. The optimiser should therefore rank candidates by bytes recoverable, and the UI should surface that ranking rather than asking the user to guess.

Tune headroom — a cost, but not a blocking one

Storing off-rate consumes part of the Sample Tune field, because the machine writes Tune = 12 × log₂(rate/44100) + musical offset into a single ±64.00 semitone field. Verified directly against the factory bank — the minimum tune observed at each rate equals the predicted compensation to the hundredth (24 000 Hz: all six samples at exactly −10.53).

Even the most aggressive tier leaves ample room: 11 025 Hz costs −24.00 st, leaving −40 … +64 st of musical transposition. This is a real but non-blocking cost.

UX consequence — show musical tune, not stored tune

Because the field mixes two concerns, a 22 050 Hz sample at its natural pitch displays as −12.00, which reads as "detuned" when it is not. The editor must display musical tune = stored tune − rate compensation, so an untransposed sample always reads 0.00 whatever its storage rate, with the compensation shown separately as a derived, read-only value.

The scoreboard — estimate, never re-encode PROTOTYPED

Requirement: the meter must show what any configuration of per-sample rates would cost before converting anything, so the user can explore freely without waiting on repeated re-encodes.

This is not an estimate — it is exact arithmetic

The .esx stores uncompressed 16-bit PCM. There is no codec, no variable bitrate, no compression. So the cost of any sample at any rate is a closed form:

frames = round(duration_seconds × target_rate)
bytes  = frames × 2 × channels
cost   = align_up(bytes + 2, 4)

The only uncertainty is ±1 frame of resampler rounding — ±2 bytes against a 25 MB budget. Only the duration is needed, and that comes from the file header without decoding a single audio frame.

Measured: 194 real WAVs probed in 0.38 seconds, no audio decoded. spike_a/budget.py.

The allocation rule, derived from real banks

A naive frames × 2 would quietly under-report, because the machine pads. Measured across 200 factory and 79 user samples:

  • every sample's byte length is even (confirming 16-bit frames);
  • every sample's start offset is 4-byte aligned — 200/200 and 79/79;
  • the gap to the next sample is always exactly 2 or 4 bytes, never zero.

All three follow from one rule: next_start = align_up(previous_end + 2, 4). Overhead is 2–4 bytes per sample — negligible in total, but included so the scoreboard is never optimistic.

#LeverSavingAudible cost
1Duration — trim before importUnbounded. In that folder the top 5 files were 59% of the total; a single 484-second recording cost 85 MB, over 3× the whole bankNone, if trimming to the musically useful part
2Channels — fold stereo to monoExactly 2×, and frees a scarce stereo slot (only 128 exist vs 256 mono)Usually low for drums and bass
3Rate — the quality tier2× per halvingHighest — it is the bandwidth itself

Folding that folder's 96 stereo sources to mono at full CD quality frees 119 504 392 bytes — the identical saving as dropping every single sample to 22 kHz, and for most material far less audible. So the scoreboard must expose rate × channels as a matrix, not a single rate ladder, and the "fit the bank" assistant should propose mono-folding and trimming before it proposes degrading bandwidth.

Feature design

ElementBehaviour
DefaultCD (44 100 Hz) for every sample. Downgrade is always an explicit choice, never automatic.
Live scoreboardBytes used / 25 165 824 with a fill bar, seconds-remaining at each tier, and mono/stereo slot counts (256 / 128) — either can run out first. Recomputes instantly on any change because nothing is re-encoded.
What-if matrixRate ladder × mono/stereo, showing total cost and fits/doesn't for each combination.
Biggest-consumers listRanked by bytes at current settings — the fastest route to "this one file is your problem".
Per-sample tierSet in the staging bank; re-encodes from the original source file, never from an already-downgraded copy, so tiers are freely revisable without generation loss.
Live budget meterBytes used / 25 165 824 and seconds remaining, updating as tiers change. Slot count (384) tracked alongside, since either can run out first.
"Fit the bank" assistantGiven an over-budget set, propose the smallest total quality loss that fits — rank by bytes-recoverable-per-tier-step, protect anything the user has pinned, and show the proposed changes for approval rather than applying them.
PinningMark a sample "keep at CD" so the assistant never touches it. The natural home for the vocal and the kick.
AuditionA/B the converted copy against the original before committing, since the audible cost of a tier is entirely material-dependent.
Anti-aliasingDownsampling must low-pass first; ffmpeg/soxr handle this. Naive decimation would alias badly and make the feature sound broken.

Open question for the TDD: the machine plays off-rate samples by interpolating, so a 22 050 Hz sample is also subject to the ESX-1's own playback interpolation quality. Whether that reads as pleasant grit or unwanted mush is material-dependent and worth an ear test on hardware before choosing the default tier ladder. Stretch and slice parts, which time-stretch, may interact further.

A second corpus — Korg's ESX-Factory-Data.esx (20 721 848 B, 200 samples, 297 populated motion slots across 106 patterns) — settles it outright. Pattern 3, slot 0, target 102 (Drum4 Filter Cutoff):

steps  0..5     128 128 128 128 128 128           <- disabled, motion has not started
steps  6..63     35  31  33 ... 117 126 127 127   <- a real filter sweep
steps 64..127   128 128 128 ... 128 128 128       <- disabled: pattern is 64 steps long

The trailing block begins exactly at the pattern's length. So 128 is both the "no update at this step" marker and the fill for steps beyond the pattern length — the editor must mask those rather than draw them as data.

NEWDiscrete parameters store knob positions, not option indices

This would have been an easy and damaging thing to get wrong. A discrete parameter divides the 0–127 knob range into N zones and stores the zone base value:

KindNObserved bytesRule
Roll, Effect Send, Amp EG, Reverse2{0, 64}i × 64
Effect Select (Fx1/Fx2/Fx3)3{0, 43, 86}i × 43
Filter Type (LPF/HPF/BPF/BPF+)4{0, 32, 64, 96}i × 32

General rule fitting all three: value = i × ceil(128 / N). Implemented as encode_discrete() / decode_discrete() in layout.py. The observed option counts also match the manual's enum lists exactly, independently validating them.

This resolves the manual erratum. REVERSE shows exactly two distinct values {0, 64} — boolean, as the parameter reference says. The p.71 motion table's "Disabl, 0...127" for Reverse is confirmed a typo. FX SEND likewise shows {0, 64}, boolean as printed.

OPENPitch does not follow the 0–127 rule

Pitch targets store values well outside the knob range, in two bands with a hole between them:

values < 128 : 103 distinct, range   0..115
values > 128 :  40 distinct, range 167..222
values 116..166 : NONE (other than 128 = Disabl)

The most common single value is 64 (663 occurrences), behaving like a centre/held value. The manual gives PITCH = -63...+63 over ±2 octaves, which does not map obviously onto this. Read as signed two's complement the bands are +0..+115 and -89..-34 — asymmetric, with an unexplained gap.

Important caveat: this is observed usage, not the legal domain — the gap may simply be values no factory pattern happened to use. To close: record a Pitch motion sequence on the hardware sweeping the knob min → max, save, and read the array. One experiment gives the exact mapping.

Until then the editor treats Pitch as raw 0–255 and must not "helpfully" clamp it to 0–127.

Full verified encodings: research/motion_byte_encodings.md.

Character set — partial answer

Distinct bytes observed in name fields: 0123456789U_adefijlnst. Plain ASCII, and lowercase round-trips, so the convention's leading lowercase a/b stores correctly. Caveat: these names were truncated from imported WAV filenames rather than typed on the machine, so this proves what the file holds, not what the dial can enter or the LCD can render. Typing a name on the hardware using every available character remains the way to settle that — and whether # is available.

Korg's own factory bank uses eight different sample rates

This settles the Rev 2 correction beyond argument. ESX-Factory-Data.esx (200 sample slots) stores:

RateSamplesRateSamples
22 050 Hz1332 000 Hz68

Korg ships 48 kHz samples in the factory content, and arbitrary rates like 23 810 and 33 000 — the machine simply stores whatever the source WAV declared and compensates pitch via Sample Tune. Any design premise that the hardware "requires" 44.1 kHz is wrong. Pre-converting remains the right default for the reasons in §03b (memory, Tune staying at 0.00, better offline resampling), but the wizard must present it as an optimisation and permit native-rate import.

Note: the plausible-rate check in validate initially flagged the 31 250 Hz samples. That was a bug in the checker, not the bank — the manual specifies a range of 11 025–96 000 Hz, not a fixed list. Fixed.

A third bank exposed a robustness requirement

Two-Lone-Swordsman_andy_mod.esx is internally inconsistent

It round-trips byte-identically and its structure is valid, but 80 of its 233 sample headers point outside the file — offsets running as high as 57 498 852 in a 22 960 884-byte file, which also exceeds the hardware's 25 165 824-byte maximum sample memory. Those headers reference audio that is not present and could never have fitted.

Why this matters for the design: round-tripping proves a file can be read and rewritten; it does not prove the file is coherent. A bank can be self-contradictory and pass the gate perfectly. The codec therefore needs a separate validation layer that checks the claims a file makes about itself — header counts vs. occupied slots, offsets within the PCM region, currentOffset consistency, rates in range. Added as esx_probe.py validate.

The other two banks validate clean, so this is specific to that file. Worth checking whether it actually loads correctly on your ESX-1 — if it does, the machine tolerates stale headers and the editor should too (repair rather than reject); if it does not, the editor should offer to prune them.
